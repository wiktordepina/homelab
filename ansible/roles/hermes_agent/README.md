# hermes_agent

Deploys Hermes Agent ([NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)) onto a VM: host preparation, the headless install, configuration, credentials, and the two systemd units that keep it running.

## What this role does

| Layer | Result |
|------|--------|
| APT | `git`, `ripgrep`, `ffmpeg`, `nodejs`, `npm`, `python3` (+ `pip`, `venv`), `curl`, `ca-certificates`, `nftables`. These are what the upstream installer expects on the host. |
| User | System user `hermes` with home at `/home/hermes`, granted passwordless sudo via `/etc/sudoers.d/hermes-nopasswd`. The upstream installer relies on `sudo apt-get` working as the run-time user. |
| Firewall | `/etc/nftables.conf` rendered from the template, service enabled. |
| Install | `scripts/install.sh --non-interactive --skip-setup` from the tracked branch, run as `hermes`. |
| Credentials | `~/.hermes/.env` templated from `/pve/secrets/hermes.sh`. |
| Configuration | `hermes setup --non-interactive` for the baseline, then `hermes config set` for the handful of keys the homelab cares about. |
| Services | `hermes-gateway` (generated by `hermes gateway install --system`) and `hermes-dashboard` (templated here), both enabled at boot. |

## Installation and version tracking

The upstream installer is fully headless. The role fetches it to `/usr/local/src/hermes-install.sh` and runs it with `--non-interactive --skip-setup`, pointing `--dir` at `~/.hermes/hermes-agent` and `--hermes-home` at `~/.hermes`. The installer provisions its own `uv`, its own Node when the distribution's is too old, the virtualenv, and the built web UI.

**The role installs; it does not update.** The install task is guarded on the `hermes` entrypoint existing, so a converge against a host that already has Hermes leaves the version alone. Moving version is a deliberate `hermes update` on the host. This is why `hermes_branch` is `main` and not a pinned commit — the pin would only ever describe the day the host was built, and the installer refuses a `--commit` that would roll an existing install backwards anyway.

The cost of tracking `main` is real and worth stating: a rebuild lands on whatever upstream shipped that day, and a rebuild is not reproducible against an older one.

### Updates are not free

`hermes update` pulls, rebuilds, and restarts the gateway. When it fails partway — a fetch error against a force-pushed upstream branch is enough — it can leave new source files on disk while the running gateway holds the old modules in memory. The gateway executes `run_agent.py` **in-process**, so the mismatch surfaces as an `ImportError` on *every* message while the process stays up and connected to every platform. It looks like an unresponsive agent, not a crashed service.

If the agent stops answering but the service is `active`, check `~/.hermes/logs/errors.log` for an `ImportError` before anything else, and restart the gateway.

## Configuration

Upstream owns `config.yaml`. It carries a `_config_version` and gets rewritten by migrations on every update, so the role does not template it. Instead `hermes setup --non-interactive` writes the baseline once, and `hermes config set` asserts the keys listed in `hermes_config` — provider, model, terminal backend, timezone. Each is read back with `hermes config get` first so the task only reports a change when it makes one.

Only string-valued keys can be asserted this way: `hermes config get` renders booleans and integers with Python's repr, which never compares equal to the value being asserted. Anything of that shape (the API server's `enabled`/`host`/`port`) is set through `.env` instead, which Hermes honours identically.

## Credentials

Everything sensitive lives in `~/.hermes/.env` (mode `0600`), templated from environment variables exported by `/pve/secrets/hermes.sh` on the apply runner:

```sh
export HERMES_API_SERVER_KEY=…          # bearer token for the OpenAI-compatible endpoint
export HERMES_OPENROUTER_API_KEY=…
export HERMES_DEEPSEEK_API_KEY=…
export HERMES_TAVILY_API_KEY=…          # web search
export HERMES_FIRECRAWL_API_KEY=…       # web extract
export HERMES_DISCORD_BOT_TOKEN=…
export HERMES_DISCORD_ALLOWED_USERS=…
export HERMES_DISCORD_HOME_CHANNEL=…
export HERMES_TELEGRAM_BOT_TOKEN=…
export HERMES_TELEGRAM_ALLOWED_USERS=…
export HERMES_TELEGRAM_HOME_CHANNEL=…
export HERMES_HASS_TOKEN=…              # Home Assistant long-lived token
export HERMES_DASHBOARD_USER=…          # optional, see below
export HERMES_DASHBOARD_PASSWORD_HASH=… # optional, see below
```

An unset variable templates as empty, which disables that integration rather than failing the converge — a host without a Discord token simply comes up without Discord.

`HERMES_API_SERVER_KEY` is the one that matters most. It is the bearer token on the OpenAI-compatible endpoint, and that endpoint dispatches agent turns that run as `hermes` — who has passwordless sudo. Anything holding this key has root on the VM.

## Network posture

- **Inbound:** any port from the homelab subnets (`10.20.0.0/16`, the three `vmbr2` VLAN ranges, and `192.168.200.0/24`). Apps the agent builds and binds on arbitrary ports are reachable from the LAN without per-port firewall edits. Everything else dropped.
- **Outbound:** DNS/NTP to the homelab nameserver, the named internal services in `defaults/main.yaml`, and TCP `80`/`443` to anywhere.

Because `443` is open to anywhere, **the firewall does not constrain where inference traffic goes**. The provider is a configuration choice, not a network one. The role configures OpenRouter directly, with a real OpenRouter key in `.env` on this host.

### The trust boundary

The VM is the boundary, and it is a coarse one. Inside the guest:

- the terminal backend is `local`, so tool calls run unsandboxed as `hermes`;
- `hermes` holds passwordless sudo;
- the API server binds `0.0.0.0`, reachable from every homelab subnet, gated only by `API_SERVER_KEY`.

That combination means a leaked `API_SERVER_KEY`, or any LAN host that can reach `:8642`, gets arbitrary code execution as root on this VM. It does not get the rest of the homelab — no `/pve/secrets` or `/pve/terraform` mounts exist here, and egress to internal services is allowlisted — but treat 217 as a machine whose contents are exposed to whatever the agent is told to do.

Hermes prints a startup warning to this effect. It is accurate, not noise.

## Services

Both units are **system** units, enabled at boot, running as `hermes`:

- `hermes-gateway` — generated by `hermes gateway install --system --run-as-user hermes --start-on-login`. Upstream resolves the user, group, home and venv interpreter itself, which is why the role calls the CLI rather than templating a unit.
- `hermes-dashboard` — templated by this role; upstream ships no install command for it.

Earlier hand-built installs used `systemd --user` units plus `loginctl enable-linger`. The role tears those down before asserting the system units, because two supervisors competing for the same SQLite state and the same ports is worse than either alone.

Two details in the dashboard unit are load-bearing:

- `--skip-build`. Without it the dashboard runs `npm ci` and rebuilds the web UI on every start. Under `Restart=always`, any startup failure becomes a loop that burns a core and 1 GiB of RSS per attempt. The web UI is already built by the installer and rebuilt by `hermes update`.
- The bind address. Upstream removed the unauthenticated public-bind escape hatch in June 2026; `--insecure` is now a documented no-op, and a non-loopback bind **refuses to start** unless an auth provider is registered. Set `HERMES_DASHBOARD_USER` and `HERMES_DASHBOARD_PASSWORD_HASH` to keep it on the LAN; leave them unset and the role binds `127.0.0.1`, which needs an SSH tunnel to reach.

Generate the password hash on the host, from the install directory:

```sh
venv/bin/python -c "from plugins.dashboard_auth.basic import hash_password; print(hash_password('…'))"
```

## State persistence

There are **no bind-mounts** on this host. Anything the agent generates that needs to survive a rebuild — skills, memories, configuration — is pushed to dedicated repositories on the homelab Forgejo (`216`) and pulled back when the VM is re-provisioned. The 250 GiB rootfs (on the ZFS zpool) holds the working copies plus docker image layers and build scratch; none of that is treated as durable.

`~/.hermes` also accumulates live state the role does not manage and a rebuild will not restore: `state.db`, `sessions/`, `memories/`, `kanban.db`, and the skills tree. Back these up separately if they matter.

## Out of scope

The workspace UI at `~/hermes-workspace` ([outsourc-e/hermes-workspace](https://github.com/outsourc-e/hermes-workspace)) is a third-party front end and is not managed here. It authenticates to the API server with `HERMES_API_TOKEN`, which must match `API_SERVER_KEY` exactly or every request 401s and the chat silently does nothing.
